# air-bridge 설계 스케치: slide↔capture 속도 협상

기준 시점: 2026-06-22 · 상태: **방법 B 일부 구현됨(2026-07-02), 방법 A는 미결정**

> 2026-07-02 갱신: 방법 B의 "완료 자동 감지+정지 안내"와 "권장값 방향 힌트"가 구현되어
> 들어갔다(`CaptureCompletionTracker`/`LtPeelTracker`, `docs/dev/slide-capture.md` 페이싱 절).
> 방법 A는 아래 결정 게이트(복귀 광학 채널의 정책 허용 여부)에 답하기 전까지 착수하지 않는다.

`todo.md` §2(slide↔capture 페이싱)의 후속 아이디어를 정리해 둔다. 지금 코드에 들어간
것은 아니고, "할지 말지"를 정하기 전의 설계 메모다. 핵심 질문은 **송신측(slide) 속도를
수신측(capture) 상태에 맞춰 어떻게 맞추느냐**이고, 아래 두 방법으로 나뉜다.

전제(바뀌면 이 문서도 무효):

- 전송은 **LT fountain**이라 "몇 번 프레임이 빠졌다"는 개념이 없다. 수신측은 어떤 심볼이든
  distinct ~`k`개를 모으면 복원된다. → 되돌릴 정보는 "누락 목록"이 아니라 **완료 신호 /
  남은 개수 / 속도 힌트**다. (누락 번호 표시는 청크 모델에서나 필요했고 fountain이 이미 없앴다.)
- 현재 채널은 **단방향**(송신=화면, 수신=카메라)이고, `CaptureService`는 "송신측으로 보내는
  통로 없음"을 전제로 권장값을 *가이드*로만 출력한다.

---

## 결정 게이트 (먼저 답해야 하는 것)

**복귀 광학 채널이 배치 환경의 에어갭 정책에서 허용되는가?**

- 양방향 광학 링크는 그 자체가 **양방향 데이터 경로(잠재적 반출 채널)** 다. 단방향 데이터
  이동만 허용하는 환경에서는 정책 위반일 수 있다. 코드의 "no back-channel"은 게으름이 아니라
  요건일 가능성이 크다.
- **허용 → 방법 A(광학 양방향)** 검토 가치 있음.
- **불허/불확실 → 방법 B(사람 매개 루프)** 만 진행. 효과의 ~80%를 정책 위반 없이 얻는다.

---

## 방법 A: 광학 양방향 back-channel (full-duplex)

송신 PC에 카메라, 수신 PC에 (작은) 화면을 추가해 **서로 마주 보게** 한다. 송신측은 데이터 QR을
띄우고, 수신측은 제어 QR을 자기 화면에 띄워 송신측 카메라가 읽는다. = 광학 full-duplex 링크.

### 협상 범위는 "거친 폐루프"로 한정

제어 채널도 QR 속도라 **왕복 지연이 수백 ms~초**다. 프레임 단위 ACK(ARQ)은 불가. 보낼 메시지는
완료/남은량/속도방향의 거친 신호뿐이다.

제어 QR 페이로드(초안 — 데이터 프레임과 magic을 구분):

```
magic 'C','B'           # control beacon (데이터 프레임 'A','B'와 구분)
u8  type                # 0=PROGRESS, 1=DONE, 2=RATE
u16 fileId or 0xFFFF    # 전체 세션 대상이면 0xFFFF
u32 haveDistinct        # 지금까지 모은 distinct 심볼 수(전 파일 합 또는 대상 파일)
u32 needApprox          # 복원까지 더 필요한 추정 심볼 수(0이면 완료)
u8  rateHint            # 0=hold, 1=slower, 2=faster
```

### 상태 기계 (송신측)

```
PLAY(현재 page-display-ms)
  ├─ 카메라로 PROGRESS 수신 → rateHint 적용(slower면 Page↑, faster면 Page↓; 방법1 하한 20ms 클램프)
  ├─ DONE(needApprox=0) 수신 → 즉시 STOP (남은 루프 낭비 제거)  ← 가장 큰 실이득
  └─ 일정 시간 무수신 → 가이드 기본값 유지(현 단방향과 동일하게 동작)
```

### 변경 영향 범위

- 수신측: `CaptureService`에 제어 QR **인코드+자기 화면 렌더** 추가(현재 권장값 계산
  `recommendedDwellMs`/완료 판정 재사용). 작은 control-display 창 또는 GUI 패널.
- 송신측: `slide`에 **카메라 grab + 제어 QR 디코드** 경로 추가(= 사실상 capture의 축소판).
  현 `displayTimer`가 매 장 `getSpinnerValue(pageDisplaySpinner)`를 다시 읽으므로(방법2에서 확인)
  Page 라이브 반영은 이미 가능 → 협상값을 스피너/내부값에 써넣기만 하면 된다.
- 공통: 제어 비콘 포맷을 `QrPayloadSupport` 옆에 별도(데이터 프레임과 magic 분리). 송·수신·tests·docs
  동시 갱신(페이로드 계약 규칙).

### 장단점

- (+) **완료 시 즉시 정지** → loop 횟수·repair-overhead 추측 불확실성 제거.
- (+) 거친 자동 속도 조절(왕복 느려도 분 단위 전송엔 충분).
- (−) 하드웨어 2배(양쪽 카메라+화면), 광학 경로 2개 정렬.
- (−) **에어갭 정책 리스크**(결정 게이트). 이게 사실상 채택 가부를 가른다.
- (−) `slide` 모듈이 카메라 의존을 갖게 됨 → 모듈 의존 방향(sender가 capture 런타임 비의존) 재검토 필요.

## 방법 B: 사람 매개 권장값 루프 (현 방식 다듬기)

복귀 채널 없이, capture가 출력하는 권장값을 **운영자가 다음 패스에 반영**하는 반쪽 루프.
이미 동작 중이며(capture가 10초마다 권장 `page-display-ms` 출력), 정책 위반이 없다.

### 다듬을 점

- [x] **완료 자동 감지 + 정지 안내** — 완료(2026-07-02). decode를 기다리지 않고 `capture`가
  직접 감지한다: 고유 payload마다 fountain 프레임을 파싱해 파일별로 심볼을 집계하고
  (`CaptureCompletionTracker`), 심볼 바이트 없이 ESI 이웃 집합만으로 `LtDecoder`와 동일한
  peel을 시뮬레이션(`LtPeelTracker`)해 "지금 저장분만으로 복원 가능"을 판정. 파일별
  `[CAPTURE][DONE]` 로그 + 전체 관측 파일 복원 가능 시 "slide 정지해도 됩니다" 배너 +
  GUI 상태 `복원 가능 N/M`. (송신측엔 신호를 못 보내므로 운영자가 보고 멈춤.)
  → 방법 A의 DONE 이득(낭비 루프 제거)을 사람을 통해 근사.
- [ ] **권장값 정밀화(캘리브레이션 모드)**: 전송 전, 송신측이 알려진 패턴을 속도 램프로 한 번
  훑어 수신측이 손실 곡선을 측정 → 단일 권장 Page 값을 더 정확히 산출(`todo.md` §2 후속).
- [x] **권장값 방향 힌트** — 완료(2026-07-02). 권장 로그에 "지금 slide Page(ms)가 N보다 작으면
  올리고, 크면 N까지 내려도 됩니다"를 덧붙였다(수신측은 송신측 Page 값을 모르므로 권장 하한
  기준의 비교 문구로 표현).

### 장단점

- (+) 하드웨어 추가 0, **정책 안전**(단방향 유지).
- (+) 변경이 receiver 쪽 출력/표시에 한정 → 위험 낮음.
- (−) 사람이 루프에 있어 반응이 느리고 수동.
- (−) "끝나면 즉시 정지"가 자동이 아니라 운영자 관찰에 의존.

## 권고 (스케치 단계 결론)

1. 먼저 **결정 게이트**(복귀 채널 정책 허용 여부)에 답한다.
2. 불확실하면 **방법 B의 "완료 자동 감지+정지 안내"** 부터 한다 — 가장 큰 실이득(낭비 루프 제거)을
   정책 위반·하드웨어 추가 없이 근사한다.
3. 방법 A는 정책이 명시적으로 허용되고, 무인 고속 반복 전송 같은 ROI가 분명할 때만 착수한다.
   착수 시 제어 비콘 포맷을 데이터 프레임과 확실히 분리하고, `slide`의 카메라 의존이 모듈 경계
   원칙(`todo.md` §4)과 충돌하지 않는지 먼저 정리한다.
